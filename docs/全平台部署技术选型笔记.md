# 全平台部署与技术选型笔记

> 个人学习记录 | 整理时间：2026-07-21
> 起因：讨论 EntHub 如何部署到其他平台，延伸到全平台架构与语言选型的通用框架。

---

## 一、问题的起点

EntHub 当前是 Python/Flask + SQLite + Jinja2 的本地工具，跑在 macOS 上。想推到 Windows / Linux / Docker / 手机，怎么走？

讨论过程中逐步澄清了几个关键认知，记录如下。

---

## 二、第一个澄清：「平台」不是一回事

「部署到其他平台」听起来是一个问题，其实是三个不同的问题，性价比差很多：

| 问题 | 本质 | 改动量 |
|------|------|--------|
| **A. 换操作系统**（Windows/Linux 桌面原生跑） | 跨 OS 兼容，卡在 macOS 专属代码 | 小（1~2 天） |
| **B. 换部署位置**（Docker / NAS / 云） | 中心化服务，多端访问 | 小（1 天） |
| **C. 换设备形态**（手机 / 平板） | 在线用 PWA 简单，离线原生要重写 | 差距巨大 |

核心洞察：**做完 B（Docker），A 和 C 的大部分需求就被覆盖了**——任何 OS、任何设备的浏览器都能访问一个 HTTP 服务。除非确实需要「离线单机」，否则不值得单独做原生启动器。

---

## 三、第二个澄清：「独立运行」和「数据共享」是矛盾的

一句容易被忽略的话：**桌面/Docker 能独立运行 = 各自一份数据库**。

三台 Windows 各自跑 Flask，就是三份独立的工商库，电话去重、号码共用判断这些核心场景全废了。工商信息天然是团队/个人跨设备共享的场景（同一份号码库，多处都要查），所以正确的模型往往是：

> **一个后端 + 多个壳**，而不是「每端各自一个后端」。

在「一个后端 + 多个壳」的架构里，桌面和手机在架构上是同构的——都是客户端。区别只在于：手机一定得连别人，桌面可以选连自己还是连别人。

---

## 四、多端同步的坑：SQLite 不能直接扔进网盘

考虑过「每台电脑一份数据，用微云/OneDrive 同步数据库文件」的方案。这条路有致命问题：

### 技术层：活文件不能按文件同步

SQLite 在被使用时实际上是三个文件：`enthub.db` + `enthub.db-wal` + `enthub.db-shm`（WAL 模式下）。网盘同步工具的「看时间戳、新的覆盖旧的」逻辑完全不适用于这种关联文件组：

- 可能只同步了 `.db`，漏了 `-wal`（最近事务丢）
- 三个文件分别在不同时刻上传，端上拿到不匹配的一组（直接损坏）
- 同步时另一端正好在写，覆盖正在被写入的页（`database disk image is malformed`）

WAL 模式尤其脆弱，因为它把写操作先攒在 `-wal` 里，不定时合并回主库。

### 逻辑层：同步只能「覆盖」，不能「合并」

就算文件完美同步，还有个逻辑问题：两台机器各自录入数据，同步时谁覆盖谁？网盘的最后写赢（LWW）会让其中一条永久丢失。出问题的方式是**静默数据损坏**——最糟的那种。

### 真要离线多端同步，只有两条成熟的路

1. **cr-sqlite（CRDT）**：每端本地 SQLite，自动合并无冲突。这是唯一能真正做「多端离线编辑、自动合并」的技术。代价是改动量大，要把普通表改成 crr 表，应用层也得调整。
2. **单主写 + 多只读副本**：只在一台机器上写，其他端只读。退化成「一台主、其他都是查看端」，本质又回到中心服务，只是中心可以是离线的某台机器。

### 一个零改动的折中方案

**别同步数据库文件，同步「导入包」**：源端导出 Excel/JSON 包，扔进微云，目标端用批量导入吃进去。导入逻辑已经做了去重（按信用代码优先、规范化公司名兜底），重复导入安全。代价是没有实时同步体感，但对「一个用户、录入频率不高」的场景完全够用，换来的是数据绝对不会损坏。

## 五、核心框架：全平台是两条正交的轴

「选一门语言解决全平台」是个伪命题。全平台由两个独立的问题组成：

- **轴一：业务逻辑能在每台设备上跑吗？** 决定「断网能不能用」。逻辑跑得越广，离线能力越强。
- **轴二：界面能在每台设备上渲染吗？** 决定「长得像不像原生、体验好不好」。

把候选方案铺到这两条轴上：

| 技术栈 | 业务逻辑覆盖 | UI 覆盖 | 离线手机 | 适合谁 |
|--------|------------|--------|---------|--------|
| **Flutter/Dart** | 全平台（含 iOS/Android/桌面/Web） | 全平台，一套 UI | ✅ | UI 重、一次写完所有端 |
| **Kotlin Multiplatform** | 全平台共享逻辑 | 各端原生 UI | ✅ | 想要原生手感、UI 各写一遍 |
| **.NET MAUI (C#)** | 全平台 | 全平台，一套 UI | ✅ | 微软生态、企业内部工具 |
| **Tauri Mobile + Rust** | 全平台（Rust 核心） | Web UI 套壳 | ✅ | 要性能 + 安全 + Web 技能复用 |
| **React Native + Web** | JS/TS 全平台 | 移动原生 + 网页 | ✅（逻辑层） | JS 团队、UI 驱动 |
| **Go + Fyne/Gio** | 桌面强、手机弱 | 手机 UI 库不成熟 | ⚠️ | 后端为主、UI 简单 |
| **Python + Web/壳** | 桌面 ✅、手机 ❌ | Web 全覆盖 | ❌（手机必须联网） | 数据工具、个人用 |

**唯一「一套代码、所有端、真离线、原生体验」四全的，基本只有 Flutter 和 MAUI。** 其他方案都在某条轴上妥协。没有银弹，只有「在哪条轴上让步」的选择。

## 六、可迁移的语言选型决策清单

以后做新项目能直接套：

1. **手机要断网独立工作吗？** 不要 → 任何后端语言都行，别折腾。
2. **要离线独立？** 要 → 选能编进手机的语言（Go/Rust/C#/Kotlin），按团队熟悉度挑（个人项目优先 Go，性能敏感选 Rust，微软系选 C#）。
3. **UI 复杂度高吗？** 高 → 前端独立选（React/Vue/Flutter），后端语言不受影响。
4. **数据要多端同步吗？** 要 → 后端语言之外，还要额外选同步方案（cr-sqlite / 自定义合并），这是独立的工程问题，跟语言无关。
5. **一个人写还是团队？** 一个人 → 选自己最熟的，别追理论最优。

## 七、按项目类型分三档推荐

| 项目类型 | 推荐技术栈 | 理由 |
|---------|----------|------|
| **数据/工具类**（查询、管理、录入为主，UI 不花哨） | Python + Web/PWA + 中心服务 | 痛点在数据，不在多端原生体验。换语言是负收益 |
| **交互/内容类**（UI 重、手势多、要装手机桌面当 App） | **Flutter** | 一套 Dart 代码产出全平台，离线可用，UI 一致 |
| **平台/中台类**（要给别的程序提供能力、强调 API） | 核心拆成「服务层 + 多端壳」 | 服务层语言无所谓，壳按端挑 |

## 八、思源笔记架构拆解（Go + Web 的经典案例）

思源能做到全平台，不是用一门语言，是用**两套技术各管一条轴**拼出来的：

| 层 | 技术 | 作用 |
|----|------|------|
| **内核（kernel）** | **Go** | 业务逻辑、数据存储、文件系统、API 服务。Go 编译静态二进制，能跑桌面、能打包进 Android、能 bind 进 iOS、能塞进 Docker |
| **前端** | TypeScript + Web | 一套代码，各端复用 |
| **桌面端** | Electron | 把 Web UI 套成 Mac/Windows/Linux 应用 |
| **移动端** | Android/iOS 原生壳 | 里面渲染的还是那套 Web UI |
| **Docker** | Go 二进制容器化 | 极其简单，官方直接提供镜像 |

**关键启示**：思源选 Go，不是因为「Go 全平台」，而是 Go 解决了「业务逻辑能编进每一端」这条轴。UI 那条轴它选的是 Web。所以思源的全平台本质是——

> 一个 Go 内核跑业务逻辑 + 一套 Web UI 套不同的壳（Electron / 移动原生 / 浏览器）

代价也是诚实的：UI 是 Web 所以原生手感不如 Flutter；Electron 内存占用偏高；移动端各一套原生工程，只是 UI 共享。

**思源证明了一件事：「真·全平台 + 手机离线」是可以做到的，技术上是 Go（或 Rust）核心 + Web UI 这条路。** 难点不在语言本身，在于要不要为一个工具投入这套架构。

## 九、Tauri vs Electron：把网页变成桌面 App 的两条路

两者解决同一个问题——**怎么把一个网页变成桌面 App**。差别在壳里塞了什么：

| 维度 | Electron | Tauri |
|------|----------|-------|
| 渲染引擎 | 自带完整 Chromium | 用系统自带 WebView |
| 后端语言 | Node.js（JS/TS） | Rust |
| 安装包体积 | 大（80~150MB+） | 小（2~10MB） |
| 内存占用 | 高 | 低（几倍差距） |
| 手机支持 | 没有 | 有（Tauri 2.0，覆盖 iOS/Android） |
| 代表产品 | VS Code、Slack、Discord、Claude 桌面版 | 很多新工具，正在取代 Electron |

**Electron 逻辑**：「自带浏览器」，体积大内存吃得多（每个 App 跑了个迷你 Chrome），好处是绝对一致。
**Tauri 逻辑**：「借用系统浏览器」，又小又快，后端是 Rust 可以写性能敏感的本地逻辑，前端调。

**关键区别**：Electron 永远只能做桌面。Tauri 2.0 之后一套代码同时出 iOS/Android/macOS/Windows/Linux——变成了 Flutter、React Native 的直接竞争对手，而且因为 UI 是 Web，会写网页就能上。

### 怎么利用

- **Python 后端的项目（如现在的 EntHub）**：不适合套。Python 塞进壳里要额外打包运行时，体积比 Electron 还大、维护更麻烦。现在的「启动脚本 + Flask 服务 + 浏览器」反而更合理。
- **未来重写成 Rust/Go 内核的项目**：Tauri 是完美搭档。想象架构：Rust 核心逻辑 + Web 前端 + Tauri 打包成全平台安装包（含手机），一套代码五端原生。这是「思源式全平台」的现代版——思源是 Go + Electron/移动壳，今天对应的是 Rust + Tauri Mobile。
- **新项目选型**：没有特殊理由选 Electron 了。除非团队只会 JS 且不在乎体积，否则 Tauri 是更好的默认。

## 十、个人技术基线建议

观察自己的项目（`EntHub` / `DoukHub` / `WebHub` / `CRM` 等）有个共同模式：本地数据 + 查询 + API 的同构小工具。与其逐个项目纠结语言，不如**定一套个人技术基线**：

- **工具类**一律 Python + Flask + SQLite + PWA/壳（现状，够用）
- **要真全平台原生**，单独立项用 Flutter（或 Rust + Tauri Mobile）
- **服务/同步层**，长期看 Go 或 Rust 更稳，但只在「性能或手机离线成为真实瓶颈」时才上

这样以后每开一个新「Hub」，不用重新选型，直接落进基线。

## 十一、EntHub 的诚实结论

现在**不需要换语言**。理由是决策清单第 1 条——当前所有场景（家里多设备查、外地偶尔用），「中心服务 + 多端壳」路径全都覆盖。Python/Flask 的「手机跑不了」这个局限，在当前需求里根本没被触发。

换 Go/Rust 重写要花 30+ 天，换来的是解决一个暂时没有的问题。真正会触发换语言的条件是：**想在完全断网下用手机录入新企业并随后合并回主库**。那一天到来时，Go 或 Rust 是首选，且要配合 cr-sqlite 做冲突合并。

在那之前，性价比最高的下一步是：**Docker + `0.0.0.0` 监听 + 一把简单鉴权 + PWA**。

## 十二、部署时必须一起处理的两个坑

1. **关掉 `app.run(debug=True)`**（[app.py](../app.py)）。一旦暴露到公网，debug 模式的 Werkzeug 调试器等于一个远程代码执行口子。部署版必须关掉，用 `waitress` / `gunicorn` 跑生产 WSGI。
2. **鉴权要和监听放开同步上，不能拖**。暴露监听的那一刻，工商电话、法人这些敏感信息就裸奔了。一个人用不用做账号体系，一把共享 API Key 或一个口令就够。

---

## 十三、关键认知（一句话总结）

- 「全平台最优语言」不存在，只有「按两条轴权衡后对你的项目最不亏的那门」。
- 「手机跑不了 Python」不等于「必须换后端语言」——取决于手机要的是壳还是本地后端。
- SQLite 是活文件，不能直接扔进网盘同步。
- 思源的全平台 = Go 内核 + Web UI + 各端壳，是「两套技术各管一条轴」的范例。
- Tauri 是 Electron 的现代替代，且额外覆盖手机端。
- 工具类项目继续用 Python 是正收益，别为不存在的问题提前付重写成本。
